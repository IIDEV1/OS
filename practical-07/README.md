## A. Каналы, сигналы, конвейер

- `pipe_demo.py`: `os.pipe()` → `fork()`; ребёнок закрывает конец чтения, пишет строку, закрывает запись; родитель закрывает свою копию записи, читает до EOF и вызывает waitpid. Результат: [pipe.txt](results/pipe.txt).
- `pipeline.py`: `ls | grep py` через два subprocess и явный `stdout=PIPE`. Код и имя файла соответствуют слайду. Вывод: [pipeline.txt](results/pipeline.txt). Список зависит от содержимого текущего каталога: здесь есть дополнительные файлы варианта B, поэтому строк больше, чем на слайде.
- `signal_demo.py`: SIGINT печатает сообщение, процесс продолжает работать. Запуск: `python3 signal_demo.py`, затем Ctrl+C в том же терминале или `kill -INT PID` в другом. Завершение — `kill -TERM PID`. Проверены и отправка SIGINT через kill, и символ Ctrl+C в псевдотерминале: драйвер терминала действительно преобразует его в сигнал.

Именованный канал вручную, терминал 1:

```bash
mkfifo /tmp/chan
ls -l /tmp/chan
cat /tmp/chan
```

Терминал 2:

```bash
echo hello > /tmp/chan
```

После проверки удалить созданный канал:

```bash
rm /tmp/chan
```

Открытие FIFO для чтения блокируется до появления писателя. После закрытия всех концов записи cat получает EOF и завершается. В автоматическом тесте проверяется, что cat ещё работает до записи и возвращает `hello` после неё; временный FIFO удаляется.

**Что делает `p1.stdout.close()`?** Закрывает лишний читающий конец канала в родительском Python-процессе. У grep остаётся своя копия, так что он продолжает читать вывод ls. Если grep завершится раньше, лишний читатель у родителя не помешает ls получить SIGPIPE/EPIPE. Строка не закрывает stdout внутри самого процесса ls.

**Как работают сигналы в коде урока?** `signal.Signals(signum).name` даёт имя сигнала. Для SIGINT установлен `handler`, выводящий «Получен SIGINT, но я не завершаюсь». Основной цикл вызывает `time.sleep(1)`. Обработчика SIGTERM нет, поэтому `kill -TERM PID` завершает процесс стандартным действием ОС. В автоматических проверках используется `python3 -u`, чтобы вывод сразу поступал в pipe; при обычном запуске в терминале достаточно команды со слайда.

Проверка обновлённых примеров: [classroom-tests.txt](results/classroom-tests.txt).

## B. Калькулятор через два FIFO

Поддерживаются числа, скобки, унарные знаки и операции `+ - * / // %`. Разбор через AST с белым списком узлов; `eval` не используется, вызовы функций, атрибуты и степень запрещены. Ограничены длина, сложность и величина результата. Ошибка деления на ноль возвращается как JSON `{"ok": false, "error": ...}`.

Два канала: `request.fifo` и `response.fifo`. Протокол — одна JSON-строка с выражением и одна JSON-строка с ответом. Клиенты этого варианта обслуживаются **строго последовательно**: общая ответная FIFO не предназначена для конкурирующих клиентов.

Терминал 1 (из папки работы):

```bash
python3 service.py fifo server "/tmp/pr7-fifo-$UID" --count 3
```

Терминал 2:

```bash
python3 service.py fifo client "/tmp/pr7-fifo-$UID" '2+3'
python3 service.py fifo client "/tmp/pr7-fifo-$UID" '8/2'
python3 service.py fifo client "/tmp/pr7-fifo-$UID" '9-7'
rmdir "/tmp/pr7-fifo-$UID"
```

Получатся 5, 4.0, 2. Сервер завершится после трёх запросов и удалит оба FIFO. При Ctrl+C/SIGTERM он также удаляет только созданные им каналы. Существующие конечные точки не перезаписываются. Результаты клиентов: [fifo_clients.json](results/fifo_clients.json).

## B. Unix-сокет: отдельный процесс на клиента

Терминал 1:

```bash
python3 service.py unix server "/tmp/pr7-calc-$UID.sock" --count 3
```

Терминал 2:

```bash
python3 service.py unix client "/tmp/pr7-calc-$UID.sock" '2+3' &
python3 service.py unix client "/tmp/pr7-calc-$UID.sock" '(8-2)*4' &
python3 service.py unix client "/tmp/pr7-calc-$UID.sock" '9/3' &
wait
```

Результаты 5, 24, 3.0 могут появиться в любом порядке. Сервер делает fork после accept, ребёнок закрывает слушающий сокет, родитель закрывает принятую копию. Для каждого клиента есть отдельное соединение; ответы не смешиваются. Родитель собирает завершившихся детей через waitpid и удаляет файл сокета. Чтение в обработчике ограничено тайм-аутом 5 секунд. Тест одновременно запускает **8 отдельных клиентских процессов**: [unix_clients.json](results/unix_clients.json).

## B. Общая память против Pipe

Передаются **10 000 000 знаковых 64-битных чисел**, каждое равно 7: 80 000 000 байт (80 МБ, около 76,3 MiB). Дочерний процесс читает все числа, проверяются размер и сумма **70 000 000**.

Для shared_memory родитель создаёт сегмент, полностью записывает массив, затем по управляющему Pipe публикует имя сегмента. Это событие готовности синхронизирует доступ. Ребёнок отображает память, суммирует данные и отправляет подтверждение. Только после подтверждения/завершения ребёнка родитель выполняет close и unlink. На пути ошибки ребёнок сначала останавливается и ожидается, затем освобождается сегмент. Проверяется, что открыть его по имени больше нельзя.

Для Pipe массив отправляется через send_bytes, а принимается через recv_bytes. Создание исходного массива и запуск ребёнка исключены из замера. Отсчёт начинается после `ready`; измерение включает создание/заполнение shm либо передачу Pipe, чтение всех чисел, суммирование и подтверждение. Поэтому это **время полного обмена с проверкой**, а не чистая пропускная способность канала. Выполнены три повтора, порядок методов чередуется.

## Измерения

| Механизм | Синхронизация | Объём запроса/массива | Время |
|---|---|---|---:|
| Два FIFO | Порядок открытия; один клиент за раз | 6 байт JSON-запроса + ответ | 136.858 мс, медиана 3 клиентов |
| Unix-сокет | Отдельное соединение/процесс; waitpid у сервера | 6 байт JSON-запроса + ответ | 221.247 мс, медиана 8 клиентов |
| SharedMemory | Явная публикация и подтверждение через управляющий Pipe | 80 000 000 байт | 0.246296 с, медиана 3 повторов |
| Pipe.send_bytes | Блокирующий канал и подтверждение приёма | 80 000 000 байт | 0.222782 с, медиана 3 повторов |

Все отдельные замеры: [benchmark.csv](results/benchmark.csv). Контрольная сумма каждого обмена проверена.

Запросы FIFO/Unix — маленькие выражения, их время включает запуск клиентского Python-процесса; в Unix-тесте клиенты параллельны. Это другой сценарий, напрямую сравнивать эти миллисекунды с передачей 80 МБ нельзя.

В текущем запуске Pipe быстрее shared_memory. Общая память позволяет избежать копирования через канал, но здесь дополнительно оплачиваются выделение сегмента и копирование исходного массива в него; чтение/проверка тоже входит во время. Повторное использование уже заполненного сегмента было бы другим экспериментом. Из одного набора измерений нельзя заключить, что Pipe всегда быстрее.

## Контрольные вопросы и вывод

**Почему общая память быстрая и опасная?** Процессы могут обращаться к одним страницам без пересылки каждого блока через ядро. Но согласованность записи/чтения автоматически не обеспечивается: без протокола готовности или блокировок возможны гонки и чтение незавершённых данных. Формулировка «самая быстрая» относится к потенциалу механизма, а не к любому сценарию с его созданием и проверками.

**Что произойдёт при записи в pipe без читателей?** В POSIX возникает SIGPIPE; если сигнал игнорируется, write возвращает EPIPE. Python обычно игнорирует SIGPIPE и сообщает BrokenPipeError.

FIFO удобен для простого последовательного сервиса; Unix-сокет — для нескольких независимых клиентов; общая память — для больших общих буферов при явной синхронизации. Проверка жизненного цикла ресурсов важна наравне с корректностью ответа.
