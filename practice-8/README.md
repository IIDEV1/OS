## A. Настоящий deadlock и исправление

`deadlock.py` создаёт два Lock. Первый поток берёт A, второй — B; барьер гарантирует, что каждый удерживает первую блокировку, прежде чем просить вторую. После этого T1 ждёт B, а T2 — A. Это воспроизводимое зависание, а не вероятностный эффект sleep.

Версия со слайда использует короткую задержку `time.sleep(0.1)`, чтобы потоки успели захватить разные блокировки. Снимок стека выполняется через 5 секунд и завершает процесс параметром `exit=True`.

```bash
timeout 3s python3 deadlock.py
echo $?  # 124
python3 fixed.py
```

Через одну секунду faulthandler выводит стеки: оба работника стоят на `with second`, главный поток — в join. Реальный вывод: [deadlock.txt](results/deadlock.txt). Без timeout программа намеренно продолжает ждать. У timeout по умолчанию SIGTERM, поэтому завершение не зависит от обработки Ctrl+C Python-потоками.

В `fixed.py` оба потока всегда берут сначала A, затем B; каждый выполняет 1000 критических секций. Результат — `[1000, 1000]`. Нарушается условие **циклического ожидания**. Остальные условия Коффмана (взаимное исключение, удержание и ожидание, отсутствие принудительного отъёма) не требуется устранять.

## A/B. Алгоритм банкира

`bank1.txt` и `bank2.txt` — JSON-файлы с available, allocation, maximum. Матрицы восстановлены по стандартному примеру, указанному в задании; отличаются только Available: (3,3,2) и (0,1,0).

Самый короткий пример из слайда можно проверить так:

```bash
python3 -c 'from banker import *; print(is_safe(AVAILABLE, ALLOCATION, MAX))'
```

Результат: `(True, ['P1', 'P3', 'P4', 'P0', 'P2'])`. Это тот же безопасный порядок, который получается в расширенном классе `Banker`; порядок безопасных процессов не обязан быть единственным.

Need = Max − Allocation:

| Процесс | Allocation | Max | Need |
|---|---|---|---|
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

Проверка безопасности работает на копии Available (`Work`). Если Need процесса ≤ Work покомпонентно, моделируется его завершение и Work увеличивается на **Allocation** этого процесса. Если незавершённые процессы есть, но ни один не подходит, состояние UNSAFE.

```bash
python3 banker.py bank1.txt
python3 banker.py bank2.txt
printf 'P1 1 0 2\n' | python3 banker.py bank1.txt --requests
```

Получено:

- bank1: **SAFE**, программа выбирает `P1 P3 P4 P0 P2`.
- bank2: **UNSAFE** — изначально нет процесса, чей Need можно удовлетворить.
- P1 запрашивает (1,0,2) на bank1: **GRANTED**; Available становится (2,3,0), Allocation[P1] = (3,0,2); новое состояние безопасно.

Безопасная последовательность не единственна. Последовательность из методички `P1 P3 P4 P2 P0` также проверяется тестом `valid_sequence` и принимается. Для неё Work изменяется: (3,3,2) → (5,3,2) → (7,4,3) → (7,4,5) → (10,4,7) → (10,5,7). Отличие порядка последних двух процессов не является ошибкой.

В режиме `--requests` читается несколько строк из stdin: `Pномер r1 r2 r3`. Проверяются границы PID, размерность, неотрицательность, Request ≤ Need и Request ≤ Available. Затем выделение пробное: если safety не проходит, исходные Available и Allocation полностью восстанавливаются. Тест запроса P4 (3,3,0) подтверждает отказ и точное совпадение состояния до/после отката. Некорректный ввод также не меняет состояние.

**UNSAFE не тождественно уже возникшему deadlock:** это отсутствие гарантированной последовательности при заявленных максимальных потребностях. Банкир избегает потенциально опасного выделения, а не ищет текущий цикл ожидания.

## B. Детектор по журналу

```bash
python3 detector.py events.txt
```

Формат событий: `acquire T1 A`, `release T1 A`, `wait T1 B`. Предполагается по одному экземпляру каждого ресурса и один текущий запрос ожидания на поток; блокировки нерекурсивные. Владельцы ресурсов и ожидающие потоки хранятся отдельно. Ребро **T1 → T2** появляется, если T1 ждёт ресурс, принадлежащий T2. Граф строится заново после события, поэтому смена владельца не оставляет старых рёбер.

Для приложенного журнала выводится **T1 → T2 → T1**. DFS использует множество активных вершин и стек пути. Это именно цикл графа ожидания потоков, а не произвольный цикл смешанного графа ресурсов. Освобождение A убирает цикл — это проверяется отдельным тестом. Неверное освобождение чужого ресурса отклоняется.

## B. TrackedLock

```bash
python3 tracked_demo.py
```

`TrackedLock` оборачивает `threading.Lock`; у группы блокировок общий Registry. Операции с графом и фактической блокировкой защищены одним Condition, чтобы владелец в графе не расходился с реальным владельцем. Ожидание выполняется в **while**, Condition освобождает свой mutex на время сна.

Перед ожиданием добавляется ребро и проверяется цикл. При обнаружении бросается `DeadlockError`; контекст `with` освобождает уже удерживаемую первую блокировку, и другой поток заканчивает. Демонстрация использует ту же схему двух встречных захватов с барьером, что и `deadlock.py`. Результат: одно исключение, один успешно завершившийся поток, пустые owners/waiting. Фактический номер потока зависит от запуска.

Ограничения: это учебная обёртка для одной группы отслеживаемых нерекурсивных lock; реализован блокирующий acquire и context manager, без совместимости со всеми режимами стандартного Lock. Она не видит обычные неотслеживаемые блокировки и произвольные ожидания I/O. Освобождение чужим потоком запрещено, повторный захват собственного lock выявляет цикл длины 1.

## B. Обедающие философы

Пять философов и пять вилок. В наивном режиме барьер после захвата левой вилки гарантирует цикл: каждый держит одну вилку и ждёт соседа. Исправления:

1. `ordered`: вилки берутся по возрастанию общего номера, исключая циклическое ожидание.
2. `waiter`: семафор допускает за стол не более N−1=4 философов; остаётся возможность завершить захват пары и освободить вилки.

```bash
timeout 4s python3 philosophers.py naive --seconds 2
python3 philosophers.py ordered --seconds 2
python3 philosophers.py waiter --seconds 2
```

| Вариант | Поел P0 | P1 | P2 | P3 | P4 | Максимальное завершённое ожидание |
|---|---:|---:|---:|---:|---:|---|
| naive | 0 | 0 | 0 | 0 | 0 | Нет завершённых захватов; deadlock |
| ordered | 606 | 635 | 640 | 648 | 606 | 4.995 мс |
| waiter | 601 | 600 | 599 | 600 | 601 | 7.468 мс |

Числа — снимок на границе примерно 2 секунд; в исправленных программах начатый приём пищи может закончиться после снимка, затем все потоки join и вилки проверяются на освобождение. Максимальное ожидание считается только для **завершённых захватов**. У зависшей версии таких захватов нет: нули в сыром поле max_completed_wait_seconds не означают отсутствие ожидания; оно уже превышает окно наблюдения и не ограничено сверху.

В обоих исправлениях на этом запуске поели все. Это подтверждает прогресс в эксперименте, но не доказывает справедливость или отсутствие голодания на любом планировщике: обычные Lock/Semaphore не обещают строгий FIFO. Задержки 1 мс моделируют еду и размышления; они не являются способом устранения deadlock.

## Контрольные вопросы и вывод

**Почему порядок ресурсов исключает deadlock?** Если все захватывают ресурсы в одном возрастающем порядке, цепочка ожиданий может двигаться только к большему номеру и не замкнётся в цикл.

**Почему банкир редко применяется в универсальной ОС?** Нужны заранее известные максимальные потребности процессов; они часто неизвестны или меняются. Кроме того, проверки и консервативные отказы имеют накладные расходы. Для локальных блокировок проще использовать порядок захвата и ограничение конкуренции.

Добавление sleep не исправляет причину deadlock. Корректность обеспечивают правила захвата и проверки состояния: упорядочивание, ограничение числа участников, анализ графа или безопасного распределения ресурсов. Намеренно зависающие программы сохранены отдельно от исправленных.
